## 2. 제품 배경 및 목표

### 2.1 배경
현재 사용자별로 할일을 독립적으로 관리하면서, 할일에 시작일과 종료일(기간)을 부여해 일정 기반으로 진행 상태(시작 전/진행중/완료/기한초과)를 자동 추적할 수 있는 서비스가 부재하다. TodoList는 이 공백을 채우기 위해, 인증 기반의 개인용 할일 관리 웹 애플리케이션으로 기획되었다.

### 2.2 제품 목표
- 사용자가 회원가입/로그인 후 자신의 할일과 카테고리를 안전하게(본인만 접근 가능하게) 관리할 수 있다.
- 할일에 시작일자·종료일자를 부여하고, 상태(시작 전/진행중/완료/기한초과)를 별도 입력 없이 자동으로 파악할 수 있다.
- 카테고리와 상태를 동시에 조합한 필터링으로 원하는 할일을 빠르게 찾을 수 있다.

### 2.3 비즈니스 목표
- 웹 우선(모바일은 반응형 웹으로만 대응)으로 빠르게 MVP를 출시한다.
- 장기적으로 최대 1000명 동시 접속을 견딜 수 있는 아키텍처 방향성을 확보한다(단, MVP 2일 일정 내 실제 부하 검증까지는 범위에 포함하지 않음 — 4.4, 8장 참조).

## 3. 목표 사용자
- 학생 및 20대~50대 직장인으로, 개인 일정·할일을 웹에서 관리하고자 하는 일반 사용자.
- 별도의 상세 페르소나 시나리오는 본 문서 범위에서 작성하지 않는다.
- 모바일 네이티브 앱 사용자는 목표 사용자에서 제외한다(반응형 웹으로만 대응).

## 4. 범위 (Scope)

2일이라는 일정과 1인 개발이라는 리소스를 고려하여, MVP 범위는 도메인 정의서의 핵심 유스케이스(UC-1~UC-9)를 충실히 구현하는 데 집중하고, 그 외 부가 기능은 과감히 제외한다.

> 참고: 4.1 In-Scope는 "이번 MVP 배포 범위에 포함되는 기능"을 뜻하며, 그 안에서도 기능별 구현 우선순위(Must/Should/Could)는 5장 기능 요구사항에서 별도로 정한다. 즉 In-Scope ≠ 전부 Must이며, 일정이 촉박해질 경우 In-Scope 내에서도 Should 항목(FR-3, FR-9)부터 먼저 축소될 수 있다.

### 4.1 In-Scope (MVP에 포함)
- 회원가입 / 로그인 (이메일 + 비밀번호 기반 인증)
- 계정 정보(닉네임, 비밀번호) 수정
- 카테고리 생성 / 수정 / 삭제 (삭제 시 '기본' 카테고리로 할일 자동 이관)
- 할일 등록 / 목록 조회 / 수정 / 삭제
- 할일 목록에서 카테고리 필터 + 상태 필터 동시 적용(AND 조건)
- 할일 상태(시작 전/진행중/완료/기한초과)의 조회 시점 자동 계산(파생값, DB 미저장)
- 반응형 웹 UI (PC/태블릿/모바일 브라우저 대응, 별도 네이티브 앱 없음)
- 기본적인 입력 유효성 검증(예: 종료일자 ≥ 시작일자) 및 에러 메시지 표시
- 소유자 기반 접근 제어(타 사용자 리소스 접근 시 404 처리)

### 4.2 Should-have / Could-have (MVP 필수는 아니지만 반영 권장, FR-11~FR-13으로 구체화)
- (Should) 할일 완료 처리 시 완료일시 자동 기록 및 목록 표시 — 도메인 정의서 3.3에서 Todo의 핵심 속성으로 이미 정의되어 있으므로 단순 Could가 아닌 Should로 취급한다(FR-11 참조)
- (Could) 카테고리별 할일 개수 표시
- (Could) 목록 정렬(마감임박순, 최신순 등)

### 4.3 Out-of-Scope (이번 MVP에서 명시적으로 제외)
- 비밀번호 재설정(이메일 인증 발송), 소셜 로그인(OAuth), 2단계 인증
- 할일 공유, 협업, 댓글, 알림(이메일/푸시) 기능
- 반복 할일(recurring todo), 서브태스크(하위 할일), 첨부파일 업로드
- 대시보드/통계/리포트, 캘린더 월간 뷰(달력형 시각화 UI)
- 다국어(i18n) 지원
- 네이티브 모바일 앱(iOS/Android), PWA 오프라인 지원
- 접근성(A11y) — 본 프로젝트에서는 범위 외로 명시한다.
- 대규모 동시접속(1000명) 부하에 대한 실제 인프라 확장(오토스케일링, 로드밸런서 다중화, CDN 등) 구축 및 부하 테스트 — MVP 단계에서는 이를 고려한 아키텍처 설계 원칙만 반영하고, 실제 검증/확장은 이후 스케일링 단계 과제로 분리한다(8장 리스크 참조).
- 자동화된 테스트(단위/통합/E2E) 스위트 전체 구축 — 시간 제약상 핵심 로직(상태 계산, 유효성 검증) 위주의 최소 검증으로 대체 가능

### 4.4 향후 로드맵 후보 (참고용, 이번 범위 아님)
비밀번호 재설정, 알림, 반복 할일, 통계 대시보드, 실측 부하테스트 및 인프라 확장.

## 5. 기능 요구사항

각 항목은 도메인 정의서의 UC-1~UC-9를 기반으로 구체화했으며, 우선순위는 Must(필수, 2일 내 반드시 구현) / Should(가능하면 포함) / Could(여력 시)로 표기한다.

### FR-1. 회원가입 (UC-1) — Must
- 이메일, 비밀번호, 닉네임을 입력받아 계정을 생성한다.
- 이메일은 로그인 계정으로 사용하며 시스템 내 유일해야 한다(중복 가입 방지).
- 비밀번호는 평문 저장하지 않고 해시(bcrypt 등)로 저장한다.
- 필수 입력값 누락, 이메일 형식 오류, 이메일 중복 시 명확한 에러 메시지를 반환한다.

### FR-2. 로그인 (UC-2) — Must
- 이메일 + 비밀번호로 인증하며, 인증 성공 시 세션/토큰(JWT 등)을 발급한다.
- 인증 실패 시 계정 존재 여부를 노출하지 않는 일반화된 에러 메시지("이메일 또는 비밀번호가 올바르지 않습니다")를 반환한다.
- 인증되지 않은 사용자는 할일/카테고리 API에 접근할 수 없다(401 처리).
- 로그아웃은 클라이언트가 보관 중인 토큰을 폐기하는 방식으로 처리한다(서버 측 블랙리스트/세션 저장소는 두지 않음 — stateless 원칙 유지). 토큰 만료 시간은 짧게(예: 1~2시간) 설정해 로그아웃 미처리로 인한 위험을 최소화한다.

### FR-3. 계정 정보 수정 (UC-3) — Should
- 로그인한 사용자는 자신의 닉네임, 비밀번호를 수정할 수 있다.
- 비밀번호 변경 시 신규 비밀번호에 대한 최소 길이 등 기본 정책을 적용한다.

### FR-4. 할일 등록 (UC-4) — Must
- 제목(필수), 설명(선택), 카테고리(선택), 시작일자(필수), 종료일자(필수)를 입력받아 할일을 생성한다.
- 시작일자/종료일자는 캘린더(날짜 선택) UI로 입력한다.
- 카테고리를 지정하지 않으면 '기본' 카테고리가 자동 적용된다.
- 종료일자는 시작일자보다 이전일 수 없다(같은 날짜는 허용). 위반 시 저장을 거부하고 유효성 오류를 반환한다.

### FR-5. 할일 목록 조회 (UC-5) — Must
- 로그인한 사용자는 자신이 소유한 할일만 목록으로 조회한다.
- 카테고리 필터와 상태 필터(시작 전/진행중/완료/기한초과)를 동시에 AND 조건으로 적용할 수 있다.
- 상태는 저장값이 아니라 완료 여부 및 서버 기준 현재일자와 시작일자·종료일자 비교를 통해 매 조회 시점에 계산한다.
- 목록은 페이지네이션 또는 최소한의 개수 제한을 적용해 대량 데이터 조회 시 성능 저하를 방지한다.

### FR-6. 할일 수정 (UC-6) — Must
- 소유자는 편집 화면에서 제목, 설명, 카테고리, 시작일자, 종료일자, 완료 여부를 수정할 수 있다. 완료 여부(Boolean) 자체의 변경은 본 항목(Must)에 포함된다.
- 완료 여부를 '완료'로 변경할 때의 완료일시 자동 기록/표시는 FR-11(Should)에서 별도로 다룬다.
- 수정 시에도 FR-4의 날짜 유효성 규칙(종료일자 ≥ 시작일자)이 동일하게 적용된다.
- 본인 소유가 아닌 할일에 대한 수정 요청은 404로 처리한다.

### FR-7. 할일 삭제 (UC-7) — Must
- 소유자는 자신의 할일을 삭제할 수 있다.
- 삭제 전 확인(컨펌) UI를 제공한다.
- 본인 소유가 아닌 할일에 대한 삭제 요청은 404로 처리한다.

### FR-8. 카테고리 생성 (UC-8) — Must
- 로그인한 사용자는 이름을 지정해 새 카테고리를 생성할 수 있다.
- 카테고리 이름은 사용자별로 중복을 허용하지 않는 것을 권장한다(동일 사용자 내 동일 이름 카테고리 중복 생성 방지).
- '기본' 카테고리는 별도 생성 없이 모든 사용자가 암묵적으로 보유한 것으로 간주하며, 사용자가 직접 삭제할 수 없다.

### FR-9. 카테고리 수정/삭제 (UC-9) — Should
- 소유자는 카테고리 이름을 수정할 수 있다.
- 소유자는 카테고리를 삭제할 수 있으며, 삭제 시 해당 카테고리에 속한 할일은 삭제되지 않고 모두 '기본' 카테고리로 자동 이관된다(트랜잭션으로 원자적 처리).
- 본인 소유가 아닌 카테고리에 대한 수정/삭제 요청은 404로 처리한다.

### FR-10. 접근 제어 공통 규칙 — Must
- 모든 할일/카테고리 API는 인증된 사용자 본인 소유 리소스에 한해서만 조회·수정·삭제를 허용한다.
- 소유자가 아닌 리소스에 대한 접근은 정보 노출을 최소화하기 위해 403이 아닌 404로 응답한다(도메인 정의서 규칙 4 준수).

### FR-11. 완료일시 자동 기록 — Should
- 할일을 '완료'로 변경하는 시점의 일시를 완료일시로 저장하고, 목록/상세에서 표시한다. 도메인 정의서 3.3의 "완료일시(선택)" 속성에 대응하는 항목이므로 단순 부가 기능이 아닌 Should로 취급한다.
- 완료 여부(Boolean) 자체의 변경은 FR-6(Must)에 포함되어 이 항목의 구현 여부와 무관하게 정상 동작해야 한다.

### FR-12. 카테고리별 할일 개수 표시 — Could
- 카테고리 목록/필터 UI에 카테고리별 할일 개수를 함께 표시한다.

### FR-13. 목록 정렬 — Could
- 할일 목록을 마감임박순, 최신 등록순 등으로 정렬할 수 있는 옵션을 제공한다.
- 미구현 시 기본 정렬(예: 등록일시 역순)만으로 대체한다.

## 6. 비기능 요구사항

### 6.1 성능
- 목표: 최대 1000명 동시 접속자를 지원할 수 있는 아키텍처 방향성을 확보한다.
  - 단, 2일 MVP 일정 내에는 실측 부하 테스트 및 인프라 확장(오토스케일링 등)까지 완료하지 않으며, 이는 8장 리스크에서 별도 과제로 분리한다.
- API 응답 시간: 목록 조회 등 주요 API는 평균 300ms 이내(로컬/단일 인스턴스 기준, p95 800ms 이내)를 목표로 한다.
- 달성 전략(설계 시점부터 반영):
  - 백엔드 API 서버는 세션을 서버 메모리에 두지 않는 stateless 구조(JWT 기반 인증)로 설계하여 수평 확장이 가능하도록 한다.
  - PostgreSQL 커넥션 풀링(pg Pool)을 적용하여 커넥션 과다 생성을 방지한다.
  - 조회 빈도가 높은 컬럼(사용자ID, 카테고리ID, 완료 여부, 종료일자)에 인덱스를 설계한다.
  - 목록 조회 API는 페이지네이션(limit/offset 또는 keyset)을 기본 적용하여 대량 데이터 조회 부하를 제한한다.
  - 필요 시 이후 단계에서 애플리케이션 레벨 캐싱(예: Redis)이나 CDN, 로드밸런서 다중화를 도입할 수 있도록 stateless 원칙을 미리 지킨다.

### 6.2 보안
- 비밀번호는 bcrypt 등 단방향 해시 알고리즘으로 저장하며, 평문 저장을 금지한다.
- 인증 토큰(JWT 등)은 적절한 만료 시간을 설정하고, HTTPS 환경에서만 전송한다.
- 모든 API 입력값은 서버 측에서 검증(길이, 형식, 날짜 유효성 등)하며, SQL Injection 방지를 위해 파라미터 바인딩(pg 라이브러리의 파라미터화 쿼리)을 사용한다.
- 사용자 간 데이터는 철저히 격리되며, 소유자 검증 없이는 어떤 CRUD 작업도 허용하지 않는다(FR-10).

### 6.3 가용성 및 안정성
- MVP 단계에서는 단일 인스턴스 운영을 전제로 하되, 무중단 배포나 다중 리전 구성은 범위 밖으로 한다.
- 서버 오류 발생 시 사용자에게 일관된 에러 응답 포맷(HTTP 상태 코드 + 메시지)을 제공한다.
- 목표 가동률(SLA)은 별도 계약 없는 개인 프로젝트 특성상 정식 지표로 설정하지 않으며, 참고용 내부 목표로 "서비스 운영 시간 중 95% 이상 정상 응답"을 지향한다.

### 6.4 사용성 및 반응형 대응
- PC, 태블릿, 모바일 브라우저에서 레이아웃이 깨지지 않는 반응형 웹 UI를 제공한다(별도 네이티브 앱 없음).
- 모바일 우선(mobile-first) 설계는 아니며, 웹(데스크톱) 우선 개발 후 반응형으로 대응한다.

### 6.5 접근성
- 본 프로젝트에서는 접근성(A11y) 요구사항을 범위 외로 명시한다.

### 6.6 유지보수성
- Prisma 등 ORM을 사용하지 않고 raw SQL / query builder(pg 라이브러리) 방식을 사용하므로, SQL 쿼리와 마이그레이션 스크립트를 별도 디렉터리로 관리하여 가독성과 추적성을 확보한다.

## 7. 기술 스택 및 아키텍처 제약

아래 기술 스택은 이미 확정된 사항으로, 대안 비교 없이 그대로 채택한다.

### 7.1 프론트엔드
- React 19 + TypeScript: 타입 안정성과 최신 React 기능(예: 개선된 렌더링/훅)을 활용해 짧은 일정에서도 버그를 줄인다.
- Zustand: 전역 클라이언트 상태(로그인 사용자 정보, 필터 상태 등)를 최소한의 보일러플레이트로 관리하기 위함. Redux 대비 러닝커브가 낮아 1인 개발/촉박한 일정에 적합.
- TanStack Query: 서버 상태(할일 목록, 카테고리 목록 등) 캐싱, 재요청, 로딩/에러 상태 관리를 표준화해 API 연동 코드량을 줄인다.

### 7.2 백엔드
- Node.js + JavaScript + Express: 빠른 API 서버 구축이 가능하고, 프론트엔드와 동일 언어(JS 계열)로 개발 생산성을 높인다.
- pg 라이브러리(Prisma 미사용): raw SQL 또는 경량 query builder 방식을 사용하여 ORM 학습/설정 비용 없이 세밀한 쿼리 제어(인덱스 활용, 파생 상태 계산 쿼리 등)를 확보한다.
- 인증: JWT 기반 stateless 인증(6.1 성능 전략과 연계).

### 7.3 데이터베이스
- PostgreSQL 17: 관계형 데이터(사용자-카테고리-할일)와 트랜잭션(카테고리 삭제 시 할일 일괄 이관 등)을 안정적으로 처리하기 위해 채택.
- 주요 테이블(개략): `users`, `categories`, `todos` (todos.status는 컬럼으로 저장하지 않고 조회 쿼리/애플리케이션 레벨에서 계산).

### 7.4 아키텍처 원칙
- Stateless API 서버: 세션을 서버 메모리에 두지 않아 향후 수평 확장(다중 인스턴스)이 가능하도록 설계한다.
- 프론트엔드(SPA)와 백엔드(REST API)를 분리하여 배포/스케일 단위를 독립적으로 가져갈 수 있게 한다.
- Prisma를 사용하지 않는 대신, SQL 쿼리를 재사용 가능한 함수/모듈 단위로 구성해 유지보수성을 확보한다.

## 9. 리스크 및 제약사항

### 9.1 핵심 긴장 관계: "1인 개발 + 2일 일정" vs "1000명 동시 접속" 목표
- 문제: 1000명 동시 접속을 실제로 안정적으로 지원하려면 부하 테스트, 인프라 확장(다중 인스턴스, 로드밸런서, 캐싱, DB 튜닝 등)이 필요하지만, 이는 1인 개발자가 2일 안에 기능 개발과 함께 수행하기 현실적으로 불가능하다.
- 완화 방안(권고):
  1. 2일 MVP는 핵심 기능(UC-1~UC-9) 완성에 집중하고, 1000명 동시 접속 대응은 이후 별도 스케일링 단계 과제로 명확히 분리한다.
  2. 다만 MVP 설계 단계에서부터 stateless API 서버, 커넥션 풀링, 인덱싱, 페이지네이션 등 "확장 가능한 구조"의 기본 원칙만은 반영하여, 이후 확장 시 재작업 비용을 최소화한다.
  3. 실제 1000명 동시 접속 검증(부하 테스트, 오토스케일링 구성)은 MVP 출시 이후 별도 일정/리소스를 확보해 진행한다.

### 9.2 기타 리스크
| 리스크 | 영향 | 완화 방안 |
|---|---|---|
| 1인 개발로 인한 병목 (질병, 예상치 못한 이슈 발생 시 전체 일정 지연) | 일정 전체 지연 | 기능 우선순위(Must/Should/Could)를 명확히 하여 Must만으로도 서비스 가능하도록 범위를 미리 축소 |

| Prisma 미사용(raw SQL)으로 인한 개발 속도 저하 가능성 | 백엔드 개발 시간 초과 | 자주 쓰는 쿼리 패턴(CRUD, 필터링)을 재사용 가능한 헬퍼 함수로 미리 정리 |
| 날짜/상태 파생 로직의 시간대(Timezone) 처리 오류 | 상태(진행중/기한초과 등) 오판정 | 서버 기준 UTC 또는 단일 시간대로 통일하여 날짜 비교 로직을 단순화 |
| 보안 미비(짧은 일정으로 인한 검증 누락) | 사용자 데이터 노출 위험 | 소유자 검증(FR-10), 비밀번호 해시, 파라미터화 쿼리는 Must 항목으로 반드시 포함 |
| 반응형 UI 대응 시간 부족 | 모바일 브라우저에서 레이아웃 깨짐 | 처음부터 반응형 CSS 프레임워크/유틸리티(예: 기본 CSS Grid/Flexbox 중심)로 단순하게 설계해 별도 조정 시간 최소화 |

## 10. 성공 지표 (KPI)

### 10.1 MVP 출시 기준(2일 내)
- Must로 표기한 기능 요구사항(FR-1, FR-2, FR-4~FR-8, FR-10)이 100% 정상 동작한다.
- 회원가입 → 로그인 → 카테고리 생성 → 할일 등록 → 목록 필터 조회 → 할일 수정/완료 → 할일 삭제 → 로그아웃까지의 핵심 사용자 흐름이 오류 없이 수행 가능하다.
- 주요 API 응답 시간(단일 사용자 기준) 평균 300ms 이내.

### 10.2 출시 이후(중장기) 지표
- 동시 접속 처리 능력: 목표 1000명 동시 접속 시에도 API 평균 응답 시간 800ms(p95) 이내 유지(별도 스케일링 단계에서 부하 테스트로 검증).
- 서비스 가동률: 운영 시간 중 95% 이상 정상 응답.
- 사용자 재방문율/할일 완료율 등은 정식 운영 이후 데이터 기반으로 별도 정의(본 MVP 단계에서는 측정 인프라 구축을 범위에 포함하지 않음).
