# TodoList 사용자 시나리오 문서

버전: 1.0 / 작성일: 2026-07-29 / 수정일: 2026-07-29 / 작성자: Business Analyst

## 1. 문서 개요

### 1.1 목적
본 문서는 `1-domain-definition.md`(도메인 정의서 v1.1)의 유스케이스(UC-1~UC-9)와
`2-PRD.md`(PRD v1.2)의 기능 요구사항(FR-1~FR-13)을 바탕으로, 목표 사용자가 실제로
서비스를 사용하는 흐름을 구체적인 시나리오 형태로 기술한다. PRD 3장에서 "상세 페르소나
시나리오는 본 문서 범위에서 작성하지 않는다"고 명시한 바 있으나, 이는 PRD 자체의 범위
제한이었을 뿐이며 본 문서에서 별도로 이를 보완한다.

### 1.2 참조 문서
- `1-domain-definition.md` (TodoList 도메인 정의서, v1.1, 2026-07-28)
- `2-PRD.md` (TodoList 제품 요구사항 문서, v1.2, 2026-07-29)

### 1.3 범위 및 제외 사항
- 본 문서의 시나리오는 PRD 4.1 In-Scope 기능(UC-1~UC-9 기반)만을 다룬다.
- PRD 4.3에서 Out-of-Scope로 명시한 기능(비밀번호 재설정, 소셜 로그인/2단계 인증,
  할일 공유·협업·댓글·알림, 반복 할일·서브태스크·첨부파일, 통계 대시보드·캘린더 월간 뷰,
  다국어, 네이티브 앱/PWA 오프라인 등)에 대한 시나리오는 다루지 않는다.
- 접근성(A11y) 관련 시나리오도 PRD 6.5에서 범위 외로 명시한 바에 따라 다루지 않는다.

## 2. 페르소나 요약

PRD 3장의 목표 사용자 정의(학생 및 20대~50대 직장인)를 대표하는 3개의 경량 페르소나를
설정한다. 배경 서사는 최소화하고 핵심 니즈 위주로 기술한다.

| 페르소나 | 직업 | 핵심 니즈 |
|---|---|---|
| P1. 김수민 | 대학생 | 과제·시험·스터디 일정을 카테고리로 나누어 관리하고, 기한이 지난 항목을 놓치지 않고 파악하고 싶다 |
| P2. 박지훈 | 30대 직장인(마케터) | 업무 태스크를 프로젝트별 카테고리로 구분하고, 진행중/완료 상태를 빠르게 필터링해 확인하고 싶다 |
| P3. 이서연 | 40대 직장인(팀장) | 업무와 개인 일정을 함께 관리하되, 완료된 항목의 처리 이력(완료일시)을 확인하고 잘못 등록한 카테고리를 정리하고 싶다 |

## 3. 페르소나별 핵심 시나리오 (정상 흐름)

### 3.1 시나리오 P1 — 학생 김수민: 과제 관리 흐름
전제: 김수민은 TodoList를 처음 사용한다.

1. 김수민은 이메일, 비밀번호, 닉네임을 입력해 회원가입한다. (UC-1/FR-1)
2. 발급된 계정으로 로그인하여 인증 토큰을 받는다. (UC-2/FR-2)
3. 카테고리 목록에서 '과제'와 '스터디' 두 개의 카테고리를 새로 생성한다. (UC-8/FR-8)
4. '과제' 카테고리로 "데이터베이스 프로젝트 보고서" 할일을 등록하며, 시작일자와
   종료일자를 캘린더 UI로 지정한다. (UC-4/FR-4)
5. 카테고리를 지정하지 않고 "동아리 회비 납부" 할일을 등록한다. 카테고리 미지정으로
   시스템이 자동으로 '기본' 카테고리를 적용한다. (UC-4/FR-4, 도메인 규칙 2)
6. 할일 목록 화면에서 카테고리 필터를 '과제'로, 상태 필터를 '진행중'으로 동시에
   설정해 오늘 처리해야 할 과제만 좁혀서 확인한다. (UC-5/FR-5)
7. "데이터베이스 프로젝트 보고서" 제출을 마치고 완료 처리한다. 완료일시가 자동
   기록되어 목록에 표시된다. (UC-6/FR-6, FR-11)
8. 이미 지난 학기에 등록해 더 이상 필요 없는 할일 하나를 삭제한다. (UC-7/FR-7)

### 3.2 시나리오 P2 — 직장인 박지훈: 업무 태스크 필터링 흐름
전제: 박지훈은 이미 가입되어 있고 로그인 상태다.

1. 박지훈은 로그인 후 '마케팅 캠페인'이라는 카테고리를 생성한다. (UC-2, UC-8/FR-2, FR-8)
2. '마케팅 캠페인' 카테고리로 "7월 SNS 콘텐츠 기획", "협력사 미팅 자료 준비" 등
   여러 건의 할일을 시작일자·종료일자와 함께 등록한다. (UC-4/FR-4)
3. 할일 목록에서 카테고리 필터('마케팅 캠페인')와 상태 필터('기한초과')를 함께 적용해
   놓친 업무가 있는지 점검한다. (UC-5/FR-5, 4장 상태 정의)
4. 기한초과로 확인된 "협력사 미팅 자료 준비"의 종료일자를 다음 주로 수정한다.
   수정 시에도 종료일자 ≥ 시작일자 유효성 규칙이 동일하게 적용된다. (UC-6/FR-6)
5. 완료된 업무는 상태 필터를 '완료'로 전환해 한 번에 확인한다. (UC-5/FR-5)
6. 더 이상 불필요해진 할일 하나를 삭제 확인(컨펌) 후 삭제한다. (UC-7/FR-7)

### 3.3 시나리오 P3 — 직장인 이서연: 계정/카테고리 정리 흐름
전제: 이서연은 이미 여러 카테고리와 할일을 등록해 사용 중이다.

1. 이서연은 로그인 후 계정 정보 화면에서 닉네임과 비밀번호를 변경한다. (UC-3/FR-3)
2. 처음에 급하게 만들었던 '기타업무' 카테고리 이름을 '팀 운영'으로 수정한다. (UC-9/FR-9)
3. 더 이상 사용하지 않는 '임시' 카테고리를 삭제한다. 해당 카테고리에 속해 있던
   할일들은 삭제되지 않고 모두 '기본' 카테고리로 자동 이관된다. (UC-9/FR-9, 도메인 규칙 7)
4. 할일 목록에서 카테고리 필터를 '기본'으로 설정해 방금 이관된 항목들이 정상적으로
   보이는지 확인한다. (UC-5/FR-5)
5. 지난주 완료 처리한 할일의 완료일시를 목록에서 확인해 언제 처리했는지 되짚어본다.
   완료된 항목은 종료일자가 지났더라도 '완료' 상태로만 표시된다. (UC-5/FR-5, FR-11, 4장/도메인 규칙 6)

## 4. 예외 및 경계 시나리오 (공통)

페르소나와 무관하게 도메인 정의서의 비즈니스 규칙 및 PRD 요구사항에서 도출되는
예외/경계 흐름이다.

### E-1. 종료일자가 시작일자보다 이전인 경우
할일을 등록하거나 수정할 때 종료일자를 시작일자보다 이전 날짜로 지정하면, 시스템은
저장 시점에 유효성 오류를 반환하고 할일을 생성·수정하지 않는다. 사용자는 오류 메시지를
확인하고 날짜를 다시 지정해야 한다. (UC-4, UC-6/FR-4, FR-6, 도메인 규칙 3)

### E-2. 카테고리를 지정하지 않고 할일을 등록하는 경우
할일 등록 화면에서 카테고리 선택을 생략하면, 시스템은 오류를 내지 않고 해당 할일에
'기본' 카테고리를 자동으로 적용해 저장한다. (UC-4/FR-4, 도메인 규칙 2)

### E-3. 카테고리 삭제 시 소속 할일의 자동 이관
사용자가 자신이 만든 카테고리를 삭제하면, 해당 카테고리에 속한 할일은 함께 삭제되지
않고 모두 '기본' 카테고리로 자동 이관된다. 이 처리는 트랜잭션으로 원자적으로 수행되어,
이관 도중 오류가 발생해도 일부 할일만 이관되는 중간 상태가 남지 않는다. (UC-9/FR-9,
도메인 규칙 7)

### E-4. '기본' 카테고리 자체는 삭제할 수 없음
모든 사용자는 별도 생성 없이도 '기본' 카테고리를 암묵적으로 보유한 것으로 간주되며,
사용자는 이 '기본' 카테고리를 직접 삭제할 수 없다. 삭제를 시도하면 시스템은 이를
거부한다. (UC-9/FR-8, FR-9)

### E-5. 타 사용자 소유 리소스에 접근하는 경우
사용자가 자신이 소유하지 않은 할일 또는 카테고리의 ID로 조회·수정·삭제를 시도하면,
시스템은 403(권한 없음)이 아니라 404(존재하지 않음)로 응답해 해당 리소스의 존재 여부
자체를 노출하지 않는다. (UC-6, UC-7, UC-9/FR-6, FR-7, FR-9, FR-10, 도메인 규칙 4)

### E-6. 완료 처리된 할일은 기한초과 여부와 무관하게 '완료' 상태 유지
종료일자가 이미 지난 할일이라도 완료 처리가 되어 있다면, 목록/필터 조회 시 상태는
'기한초과'가 아닌 '완료'로 표시된다. 상태는 완료 여부를 최우선으로 판단한 뒤,
미완료 할일에 한해서만 날짜 비교로 시작 전/진행중/기한초과를 구분한다. (UC-5, UC-6/
FR-5, FR-6, 4장 상태 정의, 도메인 규칙 6)

### E-7. 인증되지 않은 상태로 할일/카테고리 API에 접근하는 경우
로그인하지 않은 사용자가 할일 등록, 목록 조회 등 인증이 필요한 기능에 접근하면
시스템은 401로 응답하며 로그인 화면으로 안내한다. (UC-2/FR-2)

### E-8. 로그인 실패 시 계정 존재 여부 비노출
이메일 또는 비밀번호가 틀린 경우, 시스템은 "이메일이 존재하지 않습니다" 등 계정 존재
여부를 유추할 수 있는 메시지 대신 "이메일 또는 비밀번호가 올바르지 않습니다"라는
일반화된 메시지만 반환한다. (UC-2/FR-2)
